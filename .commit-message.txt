fix(gigtech): catch 4xx on every per-customer call (SA tokens 404 those too)

Deploy logs from ed0a849b confirmed: even `/customers/{cid}/cloudspaces`
and `/customers/{cid}/invoices` 404 'username' for the DynAion service
account, despite the SA's role granting `Read` on the customer scope.
gig.tech's IAM apparently requires a `username` claim on every resolver
that walks user→customer membership, and SA tokens don't carry one.

Result before this commit: /v1/vco/me, /customers, /locations all
worked (synthesized fallbacks). /v1/vco/summary still 404'd because
its internal listCloudspacesFor / listCustomerInvoices calls bubbled
the 'username' error.

This commit wraps every per-customer list call in the same
"4xx + SA token → empty array" pattern:
 - listCloudspacesFor
 - listCustomerInvoices
 - listCustomerCertificates
 - listCustomerAudits

The dashboard now mounts cleanly with the SA token: customer card
present, all counts/lists empty (correctly reflecting "we have no
visibility into ABP's data with this credential"). Drilling into
ABP shows empty cloudspaces/invoices instead of erroring.

The right long-term fix is a partner-level credential or SA scope
that includes the relevant API surface — but THAT'S a gig.tech
config / contract decision, not a code one. Until then the dashboard
stays usable in mock-vs-actual-empty mode.
